# Weekly reviewed updates and releases

On September 20, 2026, Caleb authorized a weekly Codex check that reviews, tests,
releases eligible XMage updates to Android and TestFlight, updates verified website
links, and safely merges to main. This is standing authority for the routine
path below, not permission to bypass a gate or incur charges.

## Scope and stopping conditions

- Verify the selected repository/origin, main, release ledger, active work and CI.
  Do not overwrite or duplicate a manual update, reuse an occupied worktree, or
  publish from a dirty checkout. No new revision means no rebuild or release.
- Freeze one exact upstream revision. Routine card/rules updates may receive
  recorded automated source and generated-inventory review under this authority.
  Record the reviewer, source SHA, detection/generated digests, findings and
  checks honestly. Automated review is not human review; a digest is not a review.
- Stop for unexplained catalogue losses, adapter conflicts requiring a design
  decision, major dependency/toolchain changes, new permissions/data handling,
  incompatible protocols, failed checks or unavailable required device evidence.
  Ask Caleb; never bypass protections or replace hashes to silence failures.
- Use existing free standard public GitHub runners. No paid hosting/runner,
  card verification, new account agreement, destructive cleanup or firewall change.
  Render deployment remains on hold until Caleb explicitly resumes it.

## Required sequence

1. Detect and review exact source changes with the maintenance tooling, including
   both source locks, dependencies and mobile transformations. Prepare a fresh
   isolated candidate after recording the exact reviewed detection digest.
2. Regenerate the real JVM engine and inspect inventory additions, removals,
   exclusions and hashes. Accept the separately reviewed generated digest.
   Preserve the same baseline commit between regeneration and validation. A
   pre-regeneration draft patch is not a finished update.
3. Execute maintenance validation. Integrate accepted source, exporter pins and
   the newly exported app catalogue. Check saved decks, aliases and artwork
   compatibility. Commit the final exact source.
4. Run exact-source non-simulator gates, then gated iOS and Android native builds
   when guarded engine inputs changed. Reuse artifacts only when provenance proves
   unchanged inputs. Never weaken the trusted native policy or substitute fixture
   success for real engines.
5. Verify native artifacts, app compilation/linkage, privacy, signing and relevant
   runtime acceptance separately on each platform. Preserve Game Center. Keep
   dedicated Online disabled until its separate hosting, database concurrency,
   authentication and real cross-platform gameplay gates pass.
6. Keep marketing version **0.1.1**. Check Apple and the ledger for an unused shared
   visible build and monotonically increasing Android versionCode. Publish only
   the tested signed Android APK; verify its URL and checksum. Upload iOS once,
   verify processing/internal access, then submit to the existing external group
   when Apple permits. Never cancel existing review or claim pending approval is
   external availability. Reconcile interrupted uploads before retrying.
7. When engine/bridge inputs changed, build/test the matching self-host runtime
   with the manual multiplayer packaging workflow. Publish checksum-pinned assets
   and update launcher references together; no moving executable `latest` URL.
8. Update and verify website artifact links, build labels and TestFlight status.
   Recheck required PR checks and source identity, then merge safely without force
   pushes. Record exact source, runs/artifacts, hashes, builds, links and remaining
   Apple/physical acceptance gates. Leave previous public links intact on failure.

A rollback uses a new reviewed forward/revert release, never an in-app executable
download. New costs, expanded security access or failed checks require escalation.

## Scheduling

The GitHub weekly workflow remains detection-only. The Codex heartbeat performs
the reviewed sequence above, not an unconditional detected-SHA deployment.
Schedule changes are active only after verification in Codex; the release record
must accurately state whether the updated heartbeat configuration succeeded.
