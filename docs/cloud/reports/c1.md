## What changed

### 1. Ladder options: `docs/cloud/ladder-options.md`

Three options compared with Arena and Hearthstone (notes section D), each with the exact changes for
`RankLadder.swift`, `Ranked.kt`, `ranked-cases.json` and the referee SQL, and a games-per-tier simulation at 50% and
60%:

- **A: tier floors.** Today's steps, but a loss never takes you out of your tier (Mythic can fall to Diamond IV).
- **B: Arena steps and floors (recommended).** +2/0 in Bronze, +2/−1 in Silver and Gold, +1/−1 from Platinum, A's
  floors, the underdog bonus kept, the streak bonus dropped, the reset unchanged. A 50% player reaches Platinum in about
  71 games instead of 540; Mythic at 60% takes about 183 instead of 301. One SQL function and a few lines per
  platform; no new stored state.
- **C: Hearthstone reset and climb bonus.** Everyone restarts at Bronze IV with a bonus from last season. It needs new
  stored state on all three sides and a friend-challenge change, and without a hidden rating it mixes returning
  players into Bronze.

The floor reads only the current points. You can't fall out of a tier, so "the start of your tier" is the same as
"the highest tier reached this season", and no peak is needed. That keeps imported and seeded standings, whose peak
can sit above their points, safe.

Simulator: `scripts/ranked/simulate_ladder.py` (seeded; `python3 scripts/ranked/simulate_ladder.py` reproduces the
tables in about 2 minutes).

### 2. Rank history from the server: `supabase/migrations/20261015180000_ranked_record_points.sql`

`mm_record_game` (same signature and grants) now stores the caller's `ranked_standings.points` for a ranked game,
read through `mm_ranked_current` so the season rollover happens first. It ignores `p_rank_points` entirely: never
stored and never range-checked, so older builds that send it keep working. It stores no points:

- for quick and casual games;
- for a ranked game played in an earlier UTC month (the standing has rolled over since);
- while the standing is still unseeded (`origin = 'fresh'` and no `ranked_results` yet), because `mm_ranked_seed` may
  still bring the phone's earlier progress. Otherwise a new player's backlog would chart as Bronze IV 0.

A re-sent game keeps its first row and points. File SHA-256:
`aab7dff9862ea933ecee53025e021579454d204042d3e749b14091413807cf24`.

Tests: `supabase/tests/ranked_record_points.sql`, run by `verify-ranked.mjs` right after the referee suite.

## Not verified

  tier.

## For the Mac session

- **Upload order (needed for the new migration to chart correctly).** `mm_record_game` now stores the standing at the
  moment the game arrives, but both apps upload a ranked game as soon as it is recorded, alongside `syncRank`:
  - iOS `OnDeviceRootView.swift` around line 691: `profileRecord.didRecord` uploads, while `saveResult` (around
    line 1443) runs `syncRank`.
  - Android `OnDeviceRootView.kt` lines 297 and 586 do the same.

  If the upload wins the race, the game charts the points from before its own result. On refresh, `afterRefresh`
  also uploads before `syncRank`, so backlog games go up before the seed (they then store no points). Suggested
  change on both platforms:
  - skip `didRecord`'s upload for `mode == .ranked`;
  - in `saveResult`, run `syncRank` and then `upload` for ranked games;
  - swap `afterRefresh` to `syncRank` and then `upload`.

  A person-vs-person match the other side hasn't reported yet still charts its pre-match points (up to an hour). An
  alternative with no ordering at all would be to build `rankHistory` in `mm_public_profile` from `ranked_results`
  (`points_after`, `created_at`). I did not do that because the brief asked for `mm_record_game`.
