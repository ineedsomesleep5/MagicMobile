# C5: engine game record

Cloud session C5 of the game improvement program (docs/GAME_IMPROVEMENT_PROGRAM.md, Phase 5), for R3
(TestFlight 41 / Android 25). Branch `cloud/c5-game-record`, cut from `origin/cloud/c2-engine-a` at
`41f123f`. Nothing here is released, uploaded, signed, applied live or pushed to main.

## Plan

1. Control the engine's randomness in the mobile adapter: one seeded generator for the GAME thread's
   rules code; AI search threads and AI reasoning draw from a separate unseeded source.
2. Record every decision in order: human answers at `MobileHumanPlayer.waitForResponse`, AI choices
   at the XMage player-method boundary (`priority`, targets, modes, mana, combat, ...), and concedes.
   Object IDs are random UUIDs in XMage, so the record names objects structurally (seat, deck load
   index, battlefield or stack position) instead.
3. A JVM replay entry point that rebuilds the match from the record and feeds every decision back,
   including save/resume points.
4. Real-JVM tests: AI-only and scripted-human games recorded and replayed to the same winner, turn
   count and life totals; a resumed game's record also replays.
5. `docs/cloud/game-record.md` (format, sizes, replay API, cheap server checks) and PROTOCOL.md.

## Progress

- 2026-10-15: recording and replay work on the real JVM engine. AI-only games (precon decks, 15–32
  turns, 2 and 3 AI seats with a conceded watcher), scripted-human games against 1 and 3 AIs, and a
  first soak of mixed games all replayed to the recorded winner, turn and life totals. Two engine
  nondeterminisms found and fixed in the adapter: XMage builds each library from an identity-hash
  set before the opening shuffle, and command-zone casts use the command object's copy of the
  spell ability (with commander tax). Docs and the resume-path tests are next.
