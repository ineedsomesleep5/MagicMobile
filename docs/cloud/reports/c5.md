## What changed

All engine changes are in the mobile adapter (`packages/ondevice-engine/engine/xmage/...` and two
lines of `engine/core`); upstream XMage and `prepare_upstream.py` are untouched.

1. **A game record** (`GameRecord`, `GameRecorder`). Every match records, in order: the seed, seats
   and decks; every human answer (at `MobileHumanPlayer.waitForResponse`); every AI decision at the
   XMage player-method boundary (priority, targets, modes, choices, mana payment, X, attackers,
   blockers, mulligan and the rest) together with the engine calls its reasoning made (activations,
   passes, attack and block declarations); concedes; and save/resume points. Objects are named by
   structure (seat, deck load index, battlefield or stack position), never by XMage's random UUIDs.
   Turn marks carry a state digest; a SHA-256 chain over setup, entries and end gives one `head`.
   Format, grammar, names and sizes: **docs/cloud/game-record.md**.
2. **Determinism** (`GameRandom`, `XmageEngine.build`). XMage's process-wide generator becomes a
   per-match seeded stream that only rules code on the GAME thread draws from; AI reasoning (search
   threads and AI choice code) draws from an unseeded source. Three upstream sources of run-to-run
   difference are controlled in the adapter: libraries are filled from an identity-hash set before
   the opening shuffle (now deck order first), "in a random order" library placement uses
   `Collections.shuffle`'s own generator (both seat classes now use the seeded stream), and AI search
   choices depend on time (recorded, never recomputed).
3. **Replay** (`GameReplay`). Rebuilds the match from the record and feeds every decision back,
   including a save and resume where the recorded game was restored (it saves and restores itself
   with the checkpoint code at that point). Java API and command line; checks the hash chain and the
   engine build first; stops at the first entry or turn digest that differs.
4. **Protocol** (PROTOCOL.md "Game record"): new `record` op (local only; both HostRouters already
   refuse it for guests), optional 64-bit `seed` in `create`, capability `"gameRecord": 1`.
   Checkpoints now carry the record so far (the payload gained one field; the engine build identity
   changes anyway, as with every engine change).
5. **Tests**: `RealGameRecordTests` (new, added to `test_real_engine.sh` with an 8-game soak) and
   `RealCheckpointTests` (every fresh-process restore now also replays its game's full record from
   the start through the resume).

Docs: docs/cloud/game-record.md (new), packages/ondevice-engine/docs/PROTOCOL.md, docs/LESSONS.md.

## What the apps and server must change (Mac session)

### Apps (iOS and Android, both platforms together)

1. **Keep the record with each finished game.** When a solo or ranked game reaches the `ended` phase,
   call `{"protocol":1,"op":"record","matchId":…}` before `destroy` and store the JSON gzipped with the
   game in local history (it is 1–8 KB gzipped). Skip it when `capabilities.gameRecord` is absent
   (older engine). Treat a `broken` field as "no record" (none has occurred in tests).
2. **Ranked AI games.** Take the seed from the server's ticket (see Server 1) and pass it as `create`'s
   `"seed"`. With the result, upload the record (gzipped, base64 or bytea) and its `head`. Queue it with
   the result in `pendingRankedResults` so a retry sends the same record.
3. **Privacy.** The record reveals every hand and library order: never send it to an online opponent
   or include it in shared diagnostics; local history and the ranked upload only. `HostRouter` already
   refuses the op for guests on both platforms; add a parity test that it stays refused.
4. **Checkpoints.** Nothing to change: the record travels inside the checkpoint, and a resumed game's
   record replays. Checkpoint files grow by the record (a few KB).
5. **Replay viewer (Phase 5 item, Mac).** Replays run on the JVM: `GameReplay` (Java API) or
   `java -cp $(cat build/runtime-classpath.txt) io.magicmobile.xmage.GameReplay record.json`. A
   developer viewer can step a replay by wrapping the same feed; that is not built here.
6. **Native rebuild.** Adapter sources changed, so R3 needs a fresh native engine on both platforms.

### Server (Supabase; each live change needs Caleb's OK)

1. `ranked_ai_games`: add `seed bigint not null` (server-random) and the tier's AI settings at ticket
   time. A new `mm_ranked_ai_start2(p_deck_bracket)` returns `{id, seed}` (keep the old function for
   older builds, with no record required).
2. Storage: `ranked_ai_records(game_id references ranked_ai_games, head text, engine_build text,
   record bytea (gzipped), created_at)`, size-capped (for example 256 KB), RLS on, no grants.
3. `mm_ranked_ai_result2(p_game, p_result, p_record, p_head)`: before counting a win, run the cheap
   checks in docs/cloud/game-record.md ("What the ranked server can check"): hash chain equals
   `head`; seed equals the ticket's; engine build is in a released-builds table; two seats; AI skill,
   depth, mistake rate and deck hash match the tier's pool; `end` says the human won and the AI lost;
   marks and turn/entry bounds; the time since the ticket covers the turns. A failed check settles the
   game as `unverified` (no rank change) and keeps the record for review.
4. A released-engine-builds table that the release process fills with each R3+ build's
   `EngineBuildIdentity` (the value in `setup.engine.engineBuild`).
5. Optional: a scheduled JVM job (not the phone) that replays a sample of stored records, every
   flagged one and every win that reaches a high tier, with `GameReplay`, and flags those that do not
   replay.

## NEEDS CALEB

- **What the server should do with an unverifiable win**: count it with a flag, or not count it until
  checked. Recommended: cheap checks gate the win; failed checks settle as `unverified` (no rank
  change) and keep the record.
- **Whether ranked should require a record** once R3 is out (older builds would then lose ranked AI
  wins). Recommended: require it for R3+ builds only, by engine build.
- **Honest limit**: even a full replay cannot prove the AI's choices came from the real AI (they are
  recorded, not recomputed), so a patched app that weakens its own AI still produces replayable wins.
  Closing that needs a deterministic AI (node budget instead of time) and is not in scope.
