## What changed

All engine changes are in the mobile adapter (`packages/ondevice-engine/engine/xmage/...` plus the
`record` op in `engine/core`); upstream XMage and `prepare_upstream.py` are untouched.

1. **A game record** (`GameRecord`, `GameRecorder`). Every match records, in order: the seed, seats,
   decks and player IDs; every human answer (at `MobileHumanPlayer.waitForResponse`); every AI decision
   at the XMage player-method boundary (priority, targets, modes, choices, mana payment, X, attackers,
   blockers, mulligan and the rest) together with the engine calls its reasoning made (activations,
   passes, attack and block declarations); concedes; and save/resume points. Objects are named by
   structure (seat, deck load index, token name and order, stack position, the question's own
   options), never by XMage's random UUIDs. Turn marks carry a state digest; a SHA-256 chain over setup,
   entries and end gives one `head`. Format, grammar, names and sizes: **docs/cloud/game-record.md**.
2. **Determinism** (`GameRandom`, `XmageEngine.build`, both seat classes). XMage's process-wide
   generator becomes a per-match seeded stream that only rules code on the GAME thread draws; AI
   reasoning and the app's view code draw from an unseeded source. Upstream sources of run-to-run
   difference handled in the adapter: libraries filled from an identity-hash set before the opening
   shuffle (now deck order first); "in a random order" library placement via `Collections.shuffle`'s
   own generator (now the seeded stream); hash sets of player IDs (the replay reuses the recorded
   IDs); simultaneous tokens in hash order (named by name, controller and order); AI search depending on
   time (choices recorded, never recomputed).
3. **Replay** (`GameReplay`): Java API and command line. Checks the hash chain and engine build,
   rebuilds the match, feeds every decision back, runs the same view code the live engine runs at each
   question, saves and restores itself where the recorded game was restored, and stops at the first
   entry or turn digest that differs. Replay-side failures stop the replay rather than reaching XMage's
   own rollback recovery.
4. **Protocol** (PROTOCOL.md "Game record"): `record` op (local only; both HostRouters already refuse
   it for guests), optional 64-bit `seed` in `create`, capability `"gameRecord": 1`. Checkpoints carry
   the record so far (the payload gained one field; the engine build identity changes anyway).
5. **Tests**: `RealGameRecordTests` (new; in `test_real_engine.sh` with an 8-game soak; every replay
   runs in a fresh JVM through the command line) and `RealCheckpointTests` (every fresh-process restore
   now also replays its game's whole record from the start through the resume). Two existing test rigs
   were updated for the new `Running` constructor and the seeded stream.

Docs: docs/cloud/game-record.md (new), packages/ondevice-engine/docs/PROTOCOL.md, docs/LESSONS.md
(three entries).

## Verified

All on the MagicMobile Cloud environment (JDK 21, Maven 3.9). JVM evidence only.

- `cd packages/ondevice-engine && bash scripts/build_jvm.sh && bash scripts/test_real_engine.sh`:
  **both exit 0** on the final commit's engine code (2026-10-15). Per suite: `CoreTests` and
  `FailureBoundaryTests` pass; `RealQueryTests` 21, `RealDeckValidationTests` 1, `RealControlledTurnTests`
  5, `RealControlPrivacyTests` 10, `RealCommanderRulesTests` 10, `RealPortraitProjectionTests` 12,
  `RealStackResponseTests` 6, `RealAIDiagnosticsTests` 1, `RealAIDifficultyTests` 8, `RealConcedeTests` 5,
  `RealAILifecycleTests` 8 + 8, `RealCheckpointTests` 9 (8 fresh-process restores; native metadata
  covers all 928 stream classes), **`RealGameRecordTests` 16** (6 scenarios, tamper checks and an
  8-game soak, 268 s), plus the deck, lifecycle and three `play_jvm.py` game scripts. 0 failures.
- `RealGameRecordTests`, each record replayed in a fresh JVM by
  `java -cp $(cat build/runtime-classpath.txt) io.magicmobile.xmage.GameReplay <record.json>`:
  - same seed and seats deal the same card instances (not just names) to the same hands and libraries;
  - 2 skill-1 AIs to a natural end after a watcher seat concedes (fixture and precon decks);
  - a scripted human (lands, spells, attacks) against 1 AI, then concedes;
  - a human against 3 AIs, recorded mid-game while the human's question waits (the replay stops at
    exactly that question with the same state);
  - two human seats and an AI, both humans conceding;
  - each replays to the recorded winner, turn, every seat's life/lost/left, the final digest and the
    engine error count, using every entry;
  - a changed entry fails the hash chain (`record_corrupt`), another engine build is refused unless
    `--any-build`, a `broken` record is refused, a bad `seed` is rejected.
- Soaks with `-Dmagicmobile.recordSoak=N` (mixed AI-only and human games over six decks, 2 to 4 seats):
  the last runs, after the final fixes, replayed **35 of 35** games in fresh JVMs (11–39 turns,
  404–2,936 entries, 1.2–5.6 KB gzipped). Earlier soaks of 40 and 30 games found the bugs listed in
  the commits (library hash order, command-zone casts, player-ID sets, token order, option-generator
  setup, trigger-order answers); each was fixed and re-soaked.
- `RealCheckpointTests`: every fresh-process restore's final record replays from the start through its
  save/resume point: naturally finished restored games match exactly; turn-capped ones (the cap exists
  only in that test) use every entry without a difference; the one checkpoint whose game the test
  changed by placing board features directly is exempt (and does diverge, as it should). The native
  serialization metadata check covers the new checkpoint classes.
- Sizes and timings: docs/cloud/game-record.md ("Size per game").

## Not verified

- No native build (iOS or Android), no device, no simulator. The record code is adapter code that the
  native image compiles in, but it has only run on the JVM. The new checkpoint classes are covered by
  the native metadata check in `RealCheckpointTests`, not by a native run.
- Determinism has known limits (docs/cloud/game-record.md, "Known limits"): hash-ordered iteration
  over card IDs in rules code, a few cards that shuffle with Java's own generator, and AI reasoning
  paths the adapter does not intercept. The soaks hit none after the fixes, but they cover six decks.
- No server code was written or applied (the brief leaves that to the Mac session).

## What the apps and server must change (Mac session)

### Apps (iOS and Android, both platforms together)

1. **Keep the record with each finished game.** When a solo or ranked game reaches the `ended` phase,
   call `{"protocol":1,"op":"record","matchId":…}` before `destroy` and store the JSON gzipped with the
   game in local history (it is 1–8 KB gzipped). Skip it when `capabilities.gameRecord` is absent
   (older engine). Treat a `broken` field as "no record" (none has occurred in tests).
2. **Ranked AI games.** Take the seed from the server's ticket (see Server 1) and pass it as `create`'s
   `"seed"`. With the result, upload the record (gzipped, base64 or bytea) and its `head`. Queue it with
   the result in `pendingRankedResults` so a retry sends the same record.
3. **Privacy.** The record reveals every hand and library order: never send it to an online opponent
   or include it in shared diagnostics; local history and the ranked upload only. `HostRouter` already
   refuses the op for guests on both platforms; add a parity test that it stays refused.
4. **Checkpoints.** Nothing to change: the record travels inside the checkpoint, and a resumed game's
   record replays. Checkpoint files grow by the record (a few KB).
5. **Replay viewer (Phase 5 item, Mac).** Replays run on the JVM: `GameReplay` (Java API) or
   `java -cp $(cat build/runtime-classpath.txt) io.magicmobile.xmage.GameReplay record.json`. A
   developer viewer can step a replay by wrapping the same feed; that is not built here.
6. **Native rebuild.** Adapter sources changed, so R3 needs a fresh native engine on both platforms.

### Server (Supabase; each live change needs Caleb's OK)

1. `ranked_ai_games`: add `seed bigint not null` (server-random) and the tier's AI settings at ticket
   time. A new `mm_ranked_ai_start2(p_deck_bracket)` returns `{id, seed}` (keep the old function for
   older builds, with no record required).
2. Storage: `ranked_ai_records(game_id references ranked_ai_games, head text, engine_build text,
   record bytea (gzipped), created_at)`, size-capped (for example 256 KB), RLS on, no grants.
3. `mm_ranked_ai_result2(p_game, p_result, p_record, p_head)`: before counting a win, run the cheap
   checks in docs/cloud/game-record.md ("What the ranked server can check"): hash chain equals
   `head`; seed equals the ticket's; engine build is in a released-builds table; two seats; AI skill,
   depth, mistake rate and deck hash match the tier's pool; `end` says the human won and the AI lost;
   marks and turn/entry bounds; the time since the ticket covers the turns. A failed check settles the
   game as `unverified` (no rank change) and keeps the record for review.
4. A released-engine-builds table that the release process fills with each R3+ build's
   `EngineBuildIdentity` (the value in `setup.engine.engineBuild`).
5. Optional: a scheduled JVM job (not the phone) that replays a sample of stored records, every
   flagged one and every win that reaches a high tier, with `GameReplay`, and flags those that do not
   replay.

## NEEDS CALEB

- **What the server should do with an unverifiable win**: count it with a flag, or not count it until
  checked. Recommended: cheap checks gate the win; failed checks settle as `unverified` (no rank
  change) and keep the record.
- **Whether ranked should require a record** once R3 is out (older builds would then lose ranked AI
  wins). Recommended: require it for R3+ builds only, by engine build.
- **Honest limit**: even a full replay cannot prove the AI's choices came from the real AI (they are
  recorded, not recomputed), so a patched app that weakens its own AI still produces replayable wins.
  Closing that needs a deterministic AI (node budget instead of time) and is not in scope.
